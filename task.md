# 1. ПОСТОЯННЫЕ ПРАВИЛА ПРОЕКТА

## 1.1 Общая цель сайта

Сайт должен стать полноценной системой для бизнеса Surpriz.

Клиент:
- заходит с телефона;
- быстро понимает, что компания делает;
- выбирает шоу-программу;
- выбирает персонажа;
- смотрит подробности;
- собирает праздник;
- добавляет доп. услуги;
- указывает дату, время, адрес;
- оформляет заказ;
- регистрируется только перед финальным оформлением;
- получает понятное сообщение, что менеджер свяжется.

Админ:
- управляет шоу-программами;
- управляет персонажами;
- управляет доп. услугами;
- управляет заказами;
- редактирует контент сайта;
- хранит информацию о компании;
- видит важную информацию по работе сайта;
- скачивает ежемесячную CRM-статистику;
- работает в красивой, понятной, русскоязычной админке.

---

## 1.2 Дизайн

Всегда придерживайся общего дизайна Surpriz.

Дизайн должен быть:
- праздничный;
- дружелюбный;
- детский, но не дешёвый;
- современный;
- мягкий;
- с большими округлыми карточками;
- с оранжевыми CTA-кнопками;
- с фиолетовыми акцентами;
- с понятной типографикой;
- без технического/сырого вида.

Новые страницы не должны выглядеть отдельно от сайта.
Любые новые блоки должны быть в общем стиле сайта.

Главный принцип:
сайт должен выглядеть как современный каталог праздников, а не как смесь старого WordPress, новых Flask-страниц и технических форм.

Не использовать случайные “ИИшные” градиенты, которые выглядят чужеродно.
Фоны должны быть спокойными, фирменными и аккуратными:
- белый;
- мягкий кремовый;
- светло-фиолетовый;
- очень лёгкие брендовые акценты;
- без агрессивных жёлто-фиолетовых переливов.

---

## 1.3 Mobile-first

Основной приоритет — телефон.

Большинство клиентов будут заходить и оформлять заказ с телефона.

Поэтому все новые публичные страницы, builder, checkout и админка должны проектироваться mobile-first.

Требования:
- нет горизонтального скролла;
- кнопки крупные и удобные пальцем;
- важная информация видна без долгого поиска;
- карточки компактные;
- формы понятные;
- минимум лишнего текста;
- CTA всегда легко найти;
- на ширине около 390px всё должно выглядеть аккуратно;
- первый экран должен быстро объяснять, куда нажимать;
- нельзя заставлять клиента долго скроллить до главного действия.

На телефоне визуал должен быть не “просто рабочий”, а реально удобный, красивый и продающий.

## 1.4 Бизнес-правила по оплате

Онлайн-оплаты на сайте не будет.

Нужно убрать:
- Click;
- Payme;
- Uzum;
- оплату перечислением;
- любые платежные агрегаторы;
- любые сценарии настоящей онлайн-оплаты.

Доступные способы оплаты:
- Наличными диджею после выполнения заказа.
- Переводом на карту диджею после выполнения заказа.

Финальная кнопка не должна называться “Оплатить”.

Использовать:
- “Оформить заказ”
или
- “Подтвердить заказ”.

Сообщение для наличных:
“Оплата наличными производится диджею после выполнения заказа.”

Сообщение для карты:
“Оплата переводом производится на карту диджею после выполнения заказа.”

## 1.5 Статусы заказов

Статусы должны быть только:

- Новый
- Подтвержден
- Выполнен
- Отменен

Логика:
- клиент оформляет заказ → статус “Новый”;
- менеджер звонит клиенту;
- если всё хорошо → менеджер ставит “Подтвержден”;
- если заказ неактуален → менеджер ставит “Отменен”;
- после проведения праздника → менеджер ставит “Выполнен”.

Не добавлять лишние статусы без отдельного согласования.

## 1.6 Цены

Все цены выставляются только админом через админку.

Клиент не может:
- менять цену;
- вводить свою цену;
- торговаться в builder;
- влиять на итоговую стоимость напрямую.

Фронтенд не является источником цены.

Сервер всегда сам пересчитывает цену на основе данных из админки.

На текущем этапе ценообразование простое:

Итог = цена шоу-программы из админки + выбранные активные доп. услуги из админки.

Никаких автоматических надбавок за:
- количество детей;
- адрес;
- время;
- срочность;
- длительность;
- выезд.

Если в будущем появятся надбавки, скидки или промокоды, они тоже должны управляться через админку, а не быть захардкожены.

## 1.7 Доп. услуги

Доп. услуги без количества.

Каждая доп. услуга либо выбрана, либо не выбрана.

Не делать quantity для допов.

Примеры доп. услуг:
- Аквагрим;
- Пиньята;
- Шарики;
- Подарок имениннику;
- Фотограф;
- Дополнительный персонаж;
- Продление программы;
- Украшение зоны;
- Усиленный реквизит.

## 1.8 Авторизация клиента

Клиент не должен регистрироваться в начале сборки заказа.

Правильный flow:

Гость:
- выбирает шоу;
- выбирает допы;
- выбирает персонажей;
- указывает дату, время, адрес;
- видит итог;
- нажимает “Оформить заказ”.

Только после этого:
- если он не авторизован, отправить на вход/регистрацию;
- после входа/регистрации вернуть на уже заполненный checkout;
- клиент видит свой ранее собранный заказ;
- нажимает “Подтвердить заказ”.

Draft заказа должен сохраняться до авторизации.

Админка должна выполнять роли:

1. Редактор сайта.

3. Управление шоу-программами.
4. Управление персонажами.

## ЭТАП 4 — server-side quote API

Цель:
сделать единый серверный расчёт стоимости.

Фронт отправляет только:
- выбранную программу;
- выбранные допы;
- дату;
- время;
- адрес;
- количество детей;
- комментарий.

Фронт не отправляет цену как источник истины.

Сервер проверяет:
- программа существует;
- программа активна;
- это шоу-программа;
- доп существует;
- доп активен;
- доп разрешён для выбранного шоу.

Итог:
цена шоу из админки + выбранные активные разрешённые допы.

Если доп недоступен:
- не считать его;
- вернуть предупреждение;
- не падать с ошибкой 500.

Никаких автоматических надбавок.
Никаких скидок.
Никаких коэффициентов.
Только цены из админки.

## ЭТАП 6 — draft и авторизация перед оформлением заказа

Цель:
регистрация нужна только перед финальным оформлением заказа.

Flow:

1. Гость собирает праздник.
2. Нажимает “Оформить заказ”.
3. Сборка сохраняется как draft.
4. Гостя отправляет на вход/регистрацию.
5. После входа/регистрации возвращает на checkout.
6. Checkout показывает уже заполненный заказ.
7. Клиент выбирает способ оплаты.
8. Клиент нажимает “Подтвердить заказ”.
9. Создаётся заказ со статусом “Новый”.
10. Клиент видит сообщение, что менеджер свяжется.

Способы оплаты:
- наличными диджею после выполнения заказа;
- переводом на карту диджею после выполнения заказа.

Если draft отсутствует, показать нормальное сообщение:

“Черновик заказа не найден. Пожалуйста, соберите праздник заново.”

Не использовать:
- Click;
- Payme;
- Uzum;
- онлайн-эквайринг;
- оплату перечислением.
